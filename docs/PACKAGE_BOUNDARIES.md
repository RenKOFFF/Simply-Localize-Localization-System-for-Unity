## Принятые требования

- Основная установка — OpenUPM, запасная — Git через UPM. Экспорт unitypackage не поддерживаем в нашем процессе.
- README, changelog, иллюстрации и файл лицензии остаются в корне репозитория по решению автора. Не дублировать документацию в пакет. Ссылки из Package Manager на GitHub можно добавить отдельно.
- Внутренние тесты, полигоны, генераторы и отчёты не должны входить в устанавливаемый пакет. Исходники остаются доступны в репозитории разработки.
- Служебные данные, полезные для диагностики, показывать в Inspector без возможности обычного редактирования. HideInInspector не заменяет защиту состояния через API.
- Новые несовместимые изменения обсуждать до реализации: конкретная польза, какие проекты затронуты, шаги перехода. Сохранение совместимости не является безусловным требованием ценой усложнения архитектуры.
- Расширения должны работать из скриптов пользовательского проекта без форка и редактирования пакета. Сохранять документированные точки расширения; не закрывать все public-типы механически.

## Как работал каталог до этапа 6.2

LocalizationConfigCatalogBuilder — Editor-обработчик сборки Player. Он находит LocalizationConfig в Resources через AssetDatabase и записывает строковый индекс. LocalizationConfigCatalog — данные этого индекса и код выбора конфига. Это разные части.

Пример условного проекта:

```text
Assets/Game/Resources/Settings/Main.asset      autoInitialize = true
Assets/Game/Resources/Settings/Dialogue.asset  autoInitialize = false
```

Builder запишет:

| resourcePath | configName | autoInitialize |
|---|---|---|
| Settings/Main | Main | true |
| Settings/Dialogue | Dialogue | false |

В записи нет ссылок на шрифты, аудио, изображения или таблицы переводов. При автоматическом старте Player читает индекс, выбирает Main и загружает его по точному пути Settings/Main. Загрузка зависимостей выбранного конфига и последующая загрузка переводов — отдельные действия; индекс не гарантирует ленивую загрузку всех ресурсов системы.

Если autoInitialize включён у двух конфигов, система сообщает о конфликте. Если ни у одного — автоматическая инициализация не происходит. Вызов Localization.Initialize() без аргументов имеет другое правило: требуется ровно один конфиг в Resources, независимо от autoInitialize. Явный Localization.Initialize(config) не ищет конфиг через каталог.

Перед сценой также выполняется общий автоматический поиск. Поэтому наличие собственного Bootstrap не означает, что текущая реализация вообще не читает индекс.

В Editor поиск использует актуальные метаданные AssetDatabase, а не сохранённый индекс. Перемещение конфига учитывается при следующей сборке Player. Сейчас Builder вызывается перед каждой сборкой и создаёт файл даже при отсутствии подходящих конфигов:

```text
Assets/SimplyLocalizeGenerated/Resources/SimplyLocalize/GeneratedConfigCatalog.asset
```

Фактический каталог нашего полигона содержит entries: []. Конфиги полигона передаются явно. Пустой генерируемый файл и ручная команда Rebuild Bootstrap Catalog — кандидаты на упрощение.

## Как показывать служебные данные

Предлагаемый Inspector: пояснение «Создаётся автоматически перед сборкой; изменяйте исходные конфигурации», число записей и таблица «Конфигурация / Путь / Автозапуск». Поля только для чтения; переход к исходному конфигу доступен. Для пустого индекса — объяснение, а не пустой Inspector.

Это предложение интерфейса, не уже реализованный Inspector. Для состояния через C# нужна отдельная граница доступа: запрет ввода в Inspector сам по себе не защищает публичный изменяемый список. Если меняется публичный API или сериализованное поле, переход согласовывается отдельно.

## Вариант без каталога — требует обсуждения

Можно заменить обнаружение конфигов в произвольных Resources-папках одним известным адресом стартового конфига, например Resources/SimplyLocalize/Settings.asset. Остальные конфиги передавать через ссылки или API, как и сейчас.

Польза: исчезают индекс, генератор, отдельный служебный asset и синхронизация Editor/Player по индексу. Цена: существующим пользователям автоматического обнаружения нужно перенести/переименовать стартовый конфиг или перейти на явную ссылку. Перенос с сохранением .meta сохраняет GUID, но пользовательские строковые пути загрузки требуют отдельной проверки. Поэтому нельзя обещать всем миграцию за две минуты.

Вариант согласован и реализован с окончательным путём Assets/SimplyLocalize/Resources/SimplyLocalizeSettings.asset. Каталог больше не используется.

## Расширение из пользовательского проекта

В текущем коде есть следующие точки расширения:

| Задача | Контракт |
|---|---|
| Свой источник данных | ILocalizationDataProvider и LocalizationManager.SetDataProvider / Localization.SetDataProvider |
| Свои plural-правила | IPluralRule / IDecimalPluralRule и PluralRuleProvider.RegisterRule |
| Свой фильтр ассетов | IAssetTypeFilter; обнаружение через TypeCache |
| Свой предпросмотр ассетов | IAssetPreviewRenderer; обнаружение через TypeCache |
| Своя вкладка редактора | IEditorTab и LocalizationEditorTabAttribute |

Минимальный пример дополнительной вкладки, который разработчик может поместить в Assets/Editor/GameLocalizationTab.cs своего проекта:

```csharp
using SimplyLocalize.Editor;
using SimplyLocalize.Editor.Windows.Tabs;
using UnityEngine.UIElements;

[LocalizationEditorTab("My Game", order: 100)]
public sealed class GameLocalizationTab : IEditorTab
{
    public void Build(VisualElement container)
    {
        container.Add(new Label("Настройки локализации моей игры"));
    }
}
```

Окно обнаруживает класс, создаёт экземпляр без аргументов и добавляет вкладку. Если проект использует собственный asmdef, Editor-сборке потребуется ссылка на SimplyLocalize.Editor. Пример сверён с интерфейсом и кодом обнаружения; отдельный импорт этого примера в чистый проект пока не выполнялся.

Свой провайдер не требует каталога конфигов:

```csharp
var manager = new LocalizationManager(config);
manager.SetDataProvider(myProvider);
manager.SetLanguage("pl");
var title = manager.Get("Menu/Title");
```

Здесь config и myProvider предоставляет код игры; pl должен быть настроен в конфиге. Это фрагмент использования, не реализация файлового провайдера. Статический фасад, встроенные компоненты и независимый manager имеют разные способы подключения; создание manager само по себе не перенаправляет встроенные компоненты на него.

## План этапа 6.2 — выполнен с уточнениями выше

1. Перенести внутренние регрессии за пределы src/SimplyLocalize с сохранением их запуска в нашем проекте.
2. Проверить состав npm pack/OpenUPM и Git/UPM: нет тестов и полигонов; документация остаётся снаружи по принятому решению.
3. Согласовать вариант старта локализации и только затем менять каталог/API. Если каталог остаётся — понятный Inspector только для чтения и автоматическая подготовка.
4. Исправить диагностику: Coverage учитывает loadTextData=false; настройки не обещают успешный автозапуск лишь по наличию Resources в пути.
5. Отдельно проверить расширение из пользовательского Editor-скрипта и провайдера, без изменения файлов пакета.
6. Полный прогон регрессий и чистая установка. Текущий анализ не заменяет эти проверки.

Проверка настройки игры остаётся продуктовой возможностью: Coverage и валидация выбранного конфига, без NUnit и тестовых сцен. Цель следующего развития: явный запуск полного скана с областью проверки и отменой. Сейчас Coverage по-прежнему анализирует данные при открытии вкладки; проверки сцен и шрифтов требуют отдельной реализации.
