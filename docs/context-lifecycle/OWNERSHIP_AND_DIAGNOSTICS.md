# Владение Resources, стоимость и предложение диагностики

Проверено на acb8433; дата 2026-11-17. Это объяснение существующей модели и предложение следующей работы. Панель и оптимизации не реализованы, этап 10 не начат.

## Что означает «последний пользователь»

Пользователь ресурса здесь — живой LocalizationContext, который подготовил набор. Это не автоматический поиск всех AudioSource, Renderer, переменных C# или сцен. Для Owned игра обязана отсоединить потребителей до ReleaseAsync. Неучтённые внешние ссылки требуют Borrowed.

Контекст перечисляет адреса выбранных таблиц/текстов. Реестр учитывает каждый Unity-объект по Instance ID: корень таблицы, её записи, текстуру Sprite и объявленные ILocalizationAssetDependencies. Повтор одного объекта внутри контекста не увеличивает счётчик повторно. Два контекста дают два владельца. Ожидающие запросы тоже защищают общие объекты до завершения; закрытие при отмене дожидается native-запроса.

Это **не AssetBundle**. Текущий загрузчик использует Resources.LoadAsync; освобождение Owned — Resources.UnloadAsset для учтённых объектов. Таблица с прямыми ссылками задаёт набор, но не становится бандлом. Addressables имеет собственную модель счётчиков ассетов/бандлов: released asset не обязательно означает немедленную выгрузку памяти бандла. [Unity UnloadAsset](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Resources.UnloadAsset.html), [Addressables memory management](https://docs.unity3d.com/Packages/com.unity.addressables@2.3/manual/MemoryManagement.html).

## Реальный пример

[owners.json](manual-20261116/owners.json): два Owned-контекста A и B подготовили английскую таблицу Radio. Игра запросила Radio/01. В таблице три клипа: 01, 02, 03.

| Действие | Владельцев у клипа 01 | Загружено клипов Radio | Результат |
|---|---:|---:|---|
| A и B готовы | 2 | 3 | Оба получают один и тот же Instance ID 46222 |
| A закрыт | 1 | 3 | B продолжает получать Loaded-клип |
| B закрыт | 0 | 0 | Таблица и три клипа освобождены |

A/B могут представлять, например, вступительный диалог и уже подготовленный следующий уровень. Когда вступление закончено, следующий уровень ещё пользуется тем же клипом — выгружать его нельзя. Если его ресурсы уникальны, они освобождаются независимо от общих объектов.

Счётчик не уменьшится от AudioSource.Stop: пока контекст жив, он обещает возможность повторного обращения к подготовленному клипу. Удерживается выбранная таблица целиком, включая пока не проигранные 02/03 и подготовленные fallback-наборы. Если сделать один огромный Radio на всю игру, контекст удержит крупный набор. Это причина разделять контент по времени жизни, а не создавать таблицу на каждый отдельный Get.

При отдельном Borrowed-прогоне после закрытия было **0 записей в реестре, но 3 AudioClip в Unity**. Так и должно быть: контекст не назначал себя владельцем native-выгрузки. Следовательно, будущая панель не должна объявлять всё вне реестра «выгруженным».

## Что со стоимостью

Учет предотвращает преждевременную выгрузку и повторную загрузку общих объектов, не создаёт вторую native-копию клипа только ради второго контекста. Он не бесплатен: хранятся словари/счётчики, граф обходится при подготовке, освобождение выполняется при закрытии/переключении. ResolveAsset сам не пересчитывает владельцев и не сканирует сцену.

Главные ограничения:

1. **Гранулярность таблиц и fallback.** Пока контекст нужен, его выбранные ресурсы удерживаются даже без активного воспроизведения. Подтверждено малым примером, большой расход RAM не измерен.
2. **ReleaseAsync.** В LocalizationResourceLease для каждого последнего объекта выполняется Addresses.Where(...).ToArray(). Это до O(R×A) сравнений для R освобождаемых объектов и A отслеживаемых адресов. Нужен обратный индекс Instance ID → адреса и измерение до/после, если этот участок окажется существенным. Сейчас это зарегистрированный риск SL-013, не реализованная оптимизация.
3. **Повторное открытие.** После последнего Owned ресурс выгружается; немедленный возврат потребует загрузки заново. Перекрытие времени жизни старого/нового контекстов помогает для действительно общих ресурсов. Отложенная выгрузка/кэш с бюджетом — возможная политика, но добавлять её без измерений не следует. У Addressables похожий эффект загрузки сразу после освобождения описан как asset churn в той же документации.
4. **Native-выгрузка и подготовка.** Отдельные UnloadAsset/LoadAudioData имеют свою стоимость; async-метод не переносит все вызовы Unity на рабочий поток. Логические лимиты не являются пределом байтов RAM.

15 входов/выходов и нулевой остаток клипов подтверждают функциональный контракт на малом наборе. Они не измеряют процент CPU, GPU/driver/RAM, длинный кадр или выгодность для тысяч ресурсов. Отмена и ожидание не доказывают отсутствие зависания native-операции. Большой бенчмарк в этом задании не запускался.

## Панель стоит добавить

Предлагается необязательная вкладка **Diagnostics → Resources** основного окна Simply Localize. Нужен небольшой публичный API неизменяемого диагностического снимка, чтобы собственный инструмент игры мог читать те же данные без reflection/форка. Debug-компонент на сцене для обычной настройки не нужен.

Поля таблицы:

- Тип/имя ресурса, Instance ID и адрес; название контекста, язык и fallback-источник.
- Владельцы и причина удержания: активный набор, кандидат, другой контекст, ожидающий запрос или подготовка аудио.
- Borrowed/Owned; состояния loading, ready, release requested, waiting, released. Released означает действие контекста; native unload requested/completed необходимо отличать от «RAM процесса уменьшилась».
- Время подготовки/закрытия, счётчики текущих наборов и срабатывания лимитов.
- Для закрытых ресурсов — короткая ограниченная история, например последние 256 событий, с причиной и временем. Отсутствие в истории не равно «никогда не загружался».

Диагностика хранит ID/строки/числа, а не сильные Unity-ссылки, иначе она сама может удерживать ресурсы. Сбор событий выключен по умолчанию; UI обновляет снимок по запросу или редко, без FindObjectsOfTypeAll и опроса памяти каждый кадр. Проверка реальной native-резидентности — отдельное явное действие с обозначенной стоимостью; byte-size из Profiler показывать как оценку, а недоступное значение — unknown. Обычный Release-билд не получает обязательную панель/постоянный журнал.

Кнопку «Force unload всё» в первой версии не предлагать: она нарушает договор живых потребителей. Полезнее показать «Radio/01 удерживает GameplayVoice (ru), осталось 1 владение» и дать перейти к контексту. Лимиты/автовыгрузку не менять от открытия панели.

Критерии приёмки: A/B дают 2 → 1 → 0; Borrowed не отмечается как native-unloaded; отменённый поздний запрос виден как waiting; панель не удерживает освобождённый объект и не наращивает историю бесконечно; закрытая/отключённая диагностика не создаёт постоянные выделения памяти. Для будущих Addressables источники состояния должны приходить от соответствующего провайдера, без притворного копирования правил Resources.
